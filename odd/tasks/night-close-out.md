## The rules that do not bend

1. **One merge at a time, gated on green.** `gh pr merge` never runs before every check reports a settled
   success, and `--admin` is used because the repository requires one approval it cannot get from a single
   account.
2. **Snapshots are regenerated from the merged code and inspected, never hand-merged.** Take one side to
   make the file valid, run the test with `-update`, then read the diff and prove it is the union of the
   intended changes and nothing else.
3. **After every merge, run the suite on `main` from the committed state** and read the output. A claim
   written before the command that checks it is a claim that will be wrong: one commit in this history did
   exactly that and needed a correction commit.
4. **Efficiency never means dropping coverage.** Every removed, skipped or shortened test names what
   covered that behaviour before and where it covers it now.
5. **Nothing is committed while a writer is still editing that worktree**, and a writer never commits.
6. **A guard that can see the class beats a test that can see the instance.** The colour-leak defect is the
   example: a snapshot compared the escapes it was generated from, and the shape check stripped exactly the
   evidence, so the defect reached the user twice.

      two things to tonight's work. The procedure below is **verified against the repository and the
      published releases**, not remembered, and it has two traps found while verifying it:

      1. Bump `downstream.version` in `.downstream/version.json` (tracked, not ignored: an ordinary
         commit). Tonight's work is feature-sized, so `0.3.0` -> `0.4.0`.
      2. Fold the changelog's `Unreleased` section into `## [0.4.0] - <date>`: that is the release notes.
      3. Commit and push to `main`, then `git tag -a v0.4.0 -m "Release v0.4.0"` and push the tag.
      4. `release.yml` triggers on `v*` and builds the four binaries with
         `-X main.Version=<tag>` plus a `SHA256SUMS` file, then creates a **draft** release.
      5. Review that draft and publish it.
      6. `gh release download v0.4.0 --pattern SHA256SUMS --dir /tmp`. **Trap one: the four hashes have to
         be matched by asset name, not by line order** - the file lists each asset with the path it had
         inside the build job.
      7. Write the version and the four hashes into `homebrew-tap/Formula/dotfiles.rb`, then **copy that
         file into the `albersg/homebrew-tap` repository and commit both. Trap two: the formula lives in
         two places**, this repository is the source of truth and the tap repository is the one Homebrew
         reads, and it has to be public for `brew install albersg/tap/dotfiles` to work without
         credentials. A formula still carrying a `PLACEHOLDER_*_SHA256` installs nothing.
      8. Verify end to end: `brew uninstall dotfiles; brew install albersg/tap/dotfiles; dotfiles --version`.
         The formula's `test` block runs `dotfiles --help`, so an install that "succeeds" and cannot run
         it fails the formula instead.

      Which is worth doing because their machine is on `0.2.3`: `brew upgrade dotfiles` today gets them
      `0.3.0`, and only after this gets them tonight's installer.
